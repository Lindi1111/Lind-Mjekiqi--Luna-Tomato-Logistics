# ESA SpOC 4 – Luna Tomato Logistics
**Author:** Lind Mjekiqi

## Project Overview

This repository documents our approach to the **ESA SpOC 4 – Luna Tomato Logistics** optimization challenge.

The project focuses on developing, testing, and improving optimization algorithms for maximum-weight three-dimensional matching problems.

Our goal is to produce high-quality, feasible solutions and systematically improve their objective values.

## Problem Description

Each candidate assignment is represented by four values:

`e l d weight`

Where:
- `e` represents the first matching dimension.
- `l` represents the second matching dimension.
- `d` represents the third matching dimension.
- `weight` represents the assignment's objective value.

The objective is to maximize the total weight of selected assignments.

### Constraints

Each selected assignment must satisfy the following conditions:

1. Every `e` value can be selected at most once.
2. Every `l` value can be selected at most once.
3. Every `d` value can be selected at most once.
4. The decision vector must contain only binary values (0 or 1).

## Baseline Algorithm

Our initial implementation uses a **Greedy Matching Algorithm**.

The algorithm:

1. Sorts candidate assignments by descending weight.
2. Iterates through the sorted assignments.
3. Selects an assignment only if none of its three identifiers has been used.
4. Produces a binary decision vector.

## Improved Algorithm: Exact ILP (OR-Tools CP-SAT)

The greedy baseline was superseded by an exact Integer Linear Programming
formulation of the max-weight 3-dimensional matching problem, solved with
Google OR-Tools CP-SAT (`data/solve_matching_cpsat.py`):

- One boolean variable per candidate transfer.
- An `at_most_one` constraint per distinct `e`, `l`, and `d` value.
- Objective: maximize the integer-scaled total weight.
- Warm-started from the previous best solution at each run, then given a
  large time budget (CP-SAT uses a portfolio of LNS/RINS/local-search
  workers internally).

This is solved against the **exact same instance files and fitness
function used by the official ESA evaluator** (downloaded from
`api.optimize.esa.int`, see `data/*-eval.py` and `data/validate_official.py`).

## Advanced Problem (Trajectory Matching)

The Advanced problem additionally requires *designing* each Earth-orbit to
Moon-orbit transfer as an up-to-3-impulse trajectory in the Bi-Circular
Problem (BCP) dynamics (Earth + Moon + Sun), before the same 3D-matching
logic applies. The official evaluator depends on `pykep` and `heyoka`,
neither of which has a prebuilt wheel for the Python version available in
this environment, and both require a C++ toolchain to build from source
(unavailable here).

To work around this, `data/bcp_lib.py` re-implements the required physics
from scratch using only numpy/scipy:
- The exact BCP equations of motion (verified against the official
  evaluator's equations line by line).
- Earth/Moon orbital-element extraction and construction, derived from
  first principles (barycentric-rotating-frame <-> instantaneous-inertial
  transforms). Round-trip (elements -> state -> elements) accuracy is
  ~1e-14, far inside the official 1e-6 tolerance.

`data/shoot4.py` / `data/shoot5.py` implement a Monte-Carlo-warm-started
least-squares shooting method that jointly targets a free point on the
destination Moon orbit, successfully producing exactly-matching transfers
(sub-meter miss distance). The open problem is *cost*: naive short,
high-thrust transfers require far more ΔV than the 5000 kg wet mass budget
allows (yielding zero/negative delivered mass); finding genuinely cheap
transfers for many Earth/Moon orbit pairs is an open, compute-intensive
search (see `ADVANCED_PROGRESS.md`).
